# Cloudflare deployment

The application uses two isolated Cloudflare environments. They share the Team
401 Ops Firebase account directory, but keep scouting data and roles in separate
D1 databases.

| Environment | Branch    | Deployment                    | Worker                     | URL                                 |
| ----------- | --------- | ----------------------------- | -------------------------- | ----------------------------------- |
| Staging     | `staging` | Automatic after every push    | `team401-scouting-staging` | `https://staging.scout.team401.org` |
| Production  | `main`    | Manual workflow dispatch only | `team401-scouting`         | `https://scout.team401.org`         |

## Release flow

1. Open feature pull requests against `staging`.
2. Merge after review; staging deploys automatically.
3. Test at `staging.scout.team401.org`.
4. Open and merge a pull request from `staging` into `main`.
5. Manually run **Deploy Production** from `main`.

Configure the GitHub `production` environment to allow deployments from `main`
only and add required reviewers if desired.

## Cloudflare resources

Create these resources in the Cloudflare account that manages `team401.org`:

- Production D1: `team401-scouting`
- Production R2: `team401-scouting-files`
- Staging D1: `team401-scouting-staging`
- Staging R2: `team401-scouting-files-staging`

The deployment token needs Account / Workers / Admin, Account / D1 / Edit,
Account / Workers R2 Storage / Edit, and Zone / Workers Routes / Edit for the
`team401.org` zone. Workers Admin is needed to create Workers during their first
deployment and can be reduced to Edit afterward.

The workflows create the Worker custom domains. Remove any existing CNAME for
either exact hostname before its first deployment.

## GitHub environments

Create GitHub environments named `staging` and `production`. Add these secrets
to each environment:

- `CLOUDFLARE_ACCOUNT_ID`
- `CLOUDFLARE_API_TOKEN`
- `TBA_AUTH_KEY`
- `TBA_WEBHOOK_SECRET` (the value generated by TBA for that exact webhook)
- `MATCH13_API_KEY` (a server-side key beginning with `m13_live_`)

Add these environment variables:

- `CLOUDFLARE_D1_DATABASE_ID`
- `CLOUDFLARE_R2_BUCKET_NAME`
- `FIREBASE_WEB_API_KEY`
- `FIREBASE_PROJECT_ID`

Use the same Firebase values as the Team 401 Ops site in both environments.
Firebase web configuration identifies the Firebase project and is not a server
credential. Copy `apiKey` and `projectId` from the Ops Firebase web app config,
or from the matching Ops deployment variables. Use
`team401-scouting-files-staging` for staging R2 and
`team401-scouting-files` for production R2.

Create the Match13 key from the Match13 account page and store it only as the
`MATCH13_API_KEY` GitHub environment secret. The Worker uses it server-side to
load Match13 xP ratings from the event-team endpoint; never expose it through a
`NEXT_PUBLIC_` variable.

Match13 responses are cached centrally in D1 for five minutes per event. A
short database lease collapses simultaneous requests from multiple clients into
one upstream request, conditional requests reuse Match13 `ETag` values, and
stale ratings remain available during upstream errors or rate-limit backoff.

Each deployment applies every pending D1 migration before publishing the new
Worker.

## Monitoring and scheduled refresh

Worker logs, invocation logs, sampled traces, and Cloudflare real-time Issues
are enabled in the generated Wrangler configuration. Query logs by
`source=scheduled-tba-refresh` to inspect cron activity. The cron runs every 15
minutes; current events refresh on every run during the event window and every
six hours otherwise. A failed refresh writes a structured error and rejects the
scheduled invocation so it appears in Cloudflare Issues.

In each Cloudflare environment, configure a **Workers script errors**
notification for the corresponding Worker and select the desired email or
webhook recipients. Notification recipients are account-level Cloudflare
settings and cannot be declared safely in this repository.

## Shared Team 401 Ops accounts

Scouting accepts only Firebase Email/Password accounts that also have a profile
in the Ops Firestore `users` collection. On sign-in, the Ops roster is synced to
D1. An existing scouting user with the same email is linked in place, preserving
historical entries and their scouting role. New roster members receive the
`scout` role by default.

Create users and manage passwords in Team 401 Ops/Firebase. Manage the separate
scouting roles (`owner`, `admin`, `strategy`, `scout`, and `video`) and scouting
access under **Admin → Team members and roles**. The first valid Ops account to
sign into an empty scouting database becomes its owner. Existing database owners
remain owners. Staging and production roles remain independent because their D1
databases are independent.

Owners and admins can create named guest passes under **Admin → Team and
event** when scouting with partner teams. Active codes remain visible to
administrators so they can be resent, expire automatically, and can be revoked
immediately. D1 stores both the readable code and its verification hash. Guest
identities and scouting entries remain attributable; guests do not need Ops
accounts.

Sign in with the email and password used by Team 401 Ops. For local development, copy
`.env.example` to `.env.local`, fill in the same Firebase project values, and
run `npm run dev`.

## The Blue Alliance webhook

After deploying, create a webhook from the TBA account dashboard. Use
`https://staging.scout.team401.org/api/tba-webhook` for staging or
`https://scout.team401.org/api/tba-webhook` for production. Copy the exact secret
displayed by TBA to the matching GitHub environment as `TBA_WEBHOOK_SECRET`,
then redeploy. Do not generate a separate value.

Enable match score and schedule notifications. After clicking **Resend code**
in TBA, refresh **Admin → Team and event → TBA webhook verification** in the
scouting app and enter the received code back in TBA. The webhook accelerates
updates; client polling remains the fallback.

## Installable app and offline use

The deployed site is a Progressive Web App. On a supported browser, use
**Install app** from the account page or mobile navigation menu. On iPhone and
iPad, use Safari’s **Share → Add to Home Screen** action.

Open the app online once after each deployment so the service worker can cache
the current app shell. The last authenticated session and event pack remain on
the device, match and pit entries are queued in IndexedDB, and queued entries
synchronize automatically when connectivity returns. Recently viewed robot and
pit photos are cached for offline use and refreshed in the background. Session
credentials and general authenticated API responses are not stored in the
service-worker cache. Event caches intentionally survive sign-out on shared
scouting tablets.

To verify a release, load the installed app online, switch the browser or device
offline, close and reopen the app, complete a test entry, then reconnect and
confirm that the pending entry synchronizes.

## Dependency updates

`renovate.json` extends `github>team401/renovate-config` and targets `staging`.
The Renovate GitHub App must be installed for the repository and its onboarding
pull request must be merged. Routine updates run before 9 AM Monday in
`America/New_York`; vulnerability alerts may open at any time. Renovate pull
requests use the same formatting, lint, test, typecheck, and build checks as
other changes and are never automerged by the shared policy.
